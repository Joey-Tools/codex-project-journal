# Codex Project Journal

Public Codex skill and helper scripts for lightweight per-workstream project journals in repositories whose policy requires the workflow, that contain a valid tracked non-generated journal entry, or that have an explicit durable-state need.
The skill does not bootstrap trackers, generated indexes, or local hooks across repositories by default.
An empty `docs/project_journal/` directory or generated `INDEX.md` does not establish adoption.
Adoption checks validate exact unconflicted stage-0 regular-file blobs from the Git index, not substituted worktree paths or content.
Before any repository Git read, the helper opens one resolved Git executable with required `O_NOFOLLOW|O_NONBLOCK`, binds the selected pathname and descriptor to the same initial regular-file identity and access policy, and copies stable content under a 64 MiB ceiling and one monotonic time budget into an owner-private immutable-by-policy snapshot. It accepts only snapshotted ELF or Mach-O native launchers; script wrappers and unknown executable formats fail closed because private-copy execution cannot preserve their relative interpreter or wrapper location semantics. It requires those exact bytes to return a bounded credential-free Git 2.45-or-newer version and never executes the mutable source path. Before each command, it reopens the snapshot with required no-follow/nonblocking flags, distinguishes identity, content, and access-policy changes, and copies the verified descriptor bytes into a fresh owner-private command launch. It locks the launch directory against ordinary replacement, then repeats descriptor/path identity, access, size, and digest validation before `Popen` executes that copy with the durable source path as `argv[0]`; this preserves native Git runtime-prefix and `%(prefix)` resolution, while the copied-byte version gate fails closed when startup dependencies cannot load from the private runtime location. The self-managed launch directory remains present until the direct child reaches a verified terminal state; if terminal state is unverified, the helper retains and reports its locator. Launch-copy and process-group cleanup failures preserve the exact original exception object, type, code, arguments, and traceback while attaching bounded cleanup evidence, including on runtimes without `BaseException.add_note`. Verification, launch copying, process startup, command execution, and the initialization final check consume their single applicable monotonic deadline. These checks prevent blocking on a substituted FIFO but do not claim to preempt a single stalled regular-file kernel operation or a malicious same-UID process that can rewrite owner-private state. The helper ignores ambient Git control/configuration redirections and forbids lazy object fetching. An adoption read establishes one absolute monotonic deadline before repository resolution and binds that resolution, the initial raw index snapshot, one bounded `git cat-file --batch` session, bounded frontmatter parsing and semantic validation, structured per-path validity, and identical final raw index revalidation to the same deadline. Exact OID/type/size/content framing, entry/field/list/issue budgets, duplicate-ID group invalidation, and byte, record, and stderr bounds all fail closed.
The helper currently requires a POSIX host and rejects other platforms before selecting or executing Git; this keeps its bounded process-group and filesystem guarantees explicit instead of silently weakening them. POSIX status observation uses `WNOWAIT` so the unreaped direct child fences the PID/PGID through every bound process-group probe and signal. After Linux confirms that leader has exited, a bounded `/proc` scan excludes the retained zombie leader while proving whether any live nonleader still belongs to the group; other POSIX hosts retain signal-zero group probes. Successful and failed commands both complete process-group cleanup before the leader is reaped, so a zero-exit wrapper cannot leave a detached descendant behind. Explicit cleanup ownership states close the async-exception handoff between process-group cleanup and reap-only cleanup; the helper never signals a numeric PGID after the final reap and reports `cleanup-incomplete` if identity, ownership handoff, or cleanup cannot be verified.
Git runtime initialization and one command dispatch share a single deferred-signal lifetime. Before either begins, the POSIX helper requires working `pthread_sigmask`, `sigpending`, and synchronous `sigwait` support (using libc `sigwait` when Python does not expose it) and fails closed if any primitive is unavailable. It blocks candidate `SIGHUP`, `SIGTERM`, and `SIGQUIT` signals while installing handlers, leaves `SIG_IGN` and caller-blocked signals untouched, then records only the first managed request without doing cleanup in the handler. Bounded checkpoints route that request through process-group reaping and hook transaction-state reporting. At terminal exit the helper blocks every actually managed signal and unconditionally commits process-private Git runtime cleanup—even after a normal command—before restoring handlers; all Git subprocesses for that command have already finished, and a later in-process `main()` invocation creates a fresh runtime. A terminal cleanup with no retained runtime also clears a cached initialization failure so a repaired `PATH` can retry; incomplete cleanup keeps the retained runtime and locator-bearing error. If terminal mask acquisition fails, outer convergence still commits runtime cleanup, retries the mask only after that commit, and otherwise performs best-safe handler and known-mask restoration plus active-state reset before surfacing the original failure. While still masked it repeatedly uses `sigpending` plus `sigwait` to consume requests that arrived during cleanup or handler restoration, restores the original handlers, requeues only the recorded first signal, and atomically restores the prior mask. Thus `SIG_DFL` terminates, a custom handler runs once and may return, ignored signals remain ignored, and a signal arriving in the final check-to-unmask window sees an already terminal runtime state. When the protected action itself fails, that exact action exception remains primary even if terminal convergence also fails; bounded convergence details, existing action recovery notes, and any retained runtime cleanup locator remain attached as notes, including on Python runtimes without `BaseException.add_note`. Pending-signal reporting reserves its final bounded detail slot for a runtime cleanup issue, so a saturated action-note list cannot hide the retained locator. A cleanup failure is reported with its retained locator before original signal propagation, and the bounded CLI note remains visible when a command error also occurred.
Opt-in hook installation is POSIX-only. It accepts system configuration only when `GIT_CONFIG_NOSYSTEM=1` disables it or `GIT_CONFIG_SYSTEM` names an explicit absolute path; an implicit build-dependent system path fails closed. Explicit system and global Git configuration are snapshotted through required `O_NOFOLLOW|O_NONBLOCK` descriptors, regular-file validation, and bounded double reads without following includes. If either scope sets `core.hooksPath` or contains an unresolved include, installation stops with an actionable repo-local override that names the durable selected source Git executable rather than a process-private snapshot. Effective worktree and local hook paths are queried through trusted Git with `--type=path --null`; Git expands `%(prefix)` and preserves significant leading or trailing whitespace before root constraints are applied. Hook writes bind the complete absolute path from the filesystem root, traverse and create allowed relative components with descriptor-relative no-follow operations, retain and revalidate every ancestor binding, and inspect existing targets with required `O_NOFOLLOW|O_NONBLOCK`. An owner-private lock serializes cooperating installers. Owner-private same-directory temporary files are committed with native no-replace or exchange rename semantics; an absent-target no-replace `EEXIST` or `ENOTEMPTY` is a definite uncommitted conflict, while any other rename error immediately revalidates exact target and staged snapshots. A proved committed rename continues directory durability and final verification, a proved uncommitted rename cleans its staging file, and an uncertain result preserves and reports the recovery locator. An absent, replaced, or content-changed target otherwise fails closed, and a mismatched exchanged entry is rolled back only while the installed object is still transaction-owned. A failed or uncertain rollback preserves the displaced object under a reported recovery locator. Before displaced-hook deletion, the helper verifies both the displaced and installed objects and enters an explicit installed-target-committed state. That committed state survives temporary-entry consumption, directory fsync, and final identity/content/access-policy verification, so a failure or asynchronous interruption reports an installed target with incomplete durability or verification instead of claiming installation failed or inventing a displaced recovery object. An asynchronous interruption before that state preserves the temporary entry and reports whether it verifies as the displaced-hook recovery object; an interruption during post-commit deletion reports either a retained cleanup locator or completed cleanup and never claims a missing recovery object. Every published recovery or cleanup locator is resolved from the held root-to-directory descriptor chain, accepts renamed components only after a bounded descriptor-relative identity/access-policy match, and is emitted only after revalidating the held directory and leaf object/type/ownership/mode/size/content binding. If the current path cannot be resolved safely, the report marks it `path_unverified` and records structured directory device/inode plus leaf and held-object evidence before closing the descriptors. Target protection covers path and target object identity, type, ownership, access mode, size, and content—not benign timestamp or directory child-entry churn. These checks detect ordinary concurrent installer races; they do not claim to exclude an actively malicious same-UID process that can ignore the protocol and mutate entries after a final verified kernel operation.
Repository discovery treats `adoption_status` as the authoritative `adopted`, `unadopted`, or `inconclusive` tag; inconclusive rows include a structured `adoption_error` and null adoption fields, and consumers must not use them as unadopted evidence. Each candidate gets one deadline before bounded repository resolution, and its first adoption check immediately reuses the remaining budget instead of resetting it after the rollout scan. Auxiliary per-repository failures produce a field-keyed structured `discovery_error` and null only the affected auxiliary fields without erasing authoritative index adoption or aborting healthy repository rows. In particular, unresolved effective hook configuration makes `hooks_installed` null and the discovery row inconclusive; `false` remains reserved for an authoritative negative check.
