# Codex Project Journal

Public Codex skill and helper scripts for lightweight per-workstream project journals in repositories whose policy requires the workflow, that contain a valid tracked non-generated journal entry, or that have an explicit durable-state need.
The skill does not bootstrap trackers, generated indexes, or local hooks across repositories by default.
An empty `docs/project_journal/` directory or generated `INDEX.md` does not establish adoption.
Adoption checks validate exact unconflicted stage-0 regular-file blobs from the Git index, not substituted worktree paths or content.
Before any repository Git read, the helper opens one resolved Git executable with required `O_NOFOLLOW|O_NONBLOCK`, binds the selected pathname and descriptor to the same initial regular-file identity and access policy, and copies stable content under a 64 MiB ceiling and one monotonic time budget into an owner-private immutable-by-policy snapshot. It accepts only snapshotted ELF or Mach-O native launchers; script wrappers and unknown executable formats fail closed because private-copy execution cannot preserve their relative interpreter or wrapper location semantics. It requires those exact bytes to return a bounded credential-free Git 2.45-or-newer version and never executes the mutable source path. Before each command, it reopens the snapshot with required no-follow/nonblocking flags, distinguishes identity, content, and access-policy changes, and copies the verified descriptor bytes into a fresh owner-private command launch. It locks the launch directory against ordinary replacement, then repeats descriptor/path identity, access, size, and digest validation before `Popen` executes that copy with the durable source path as `argv[0]`; this preserves native Git runtime-prefix and `%(prefix)` resolution, while the copied-byte version gate fails closed when startup dependencies cannot load from the private runtime location. The self-managed launch directory remains present until the direct child reaches a verified terminal state; if terminal state is unverified, the helper retains and reports its locator. Launch-copy and process-group cleanup failures preserve the exact original exception object, type, code, arguments, and traceback while attaching bounded cleanup evidence, including on runtimes without `BaseException.add_note`. Verification, launch copying, process startup, command execution, and the initialization final check consume their single applicable monotonic deadline. These checks prevent blocking on a substituted FIFO but do not claim to preempt a single stalled regular-file kernel operation or a malicious same-UID process that can rewrite owner-private state. The helper ignores ambient Git control/configuration redirections and forbids lazy object fetching. An adoption read establishes one absolute monotonic deadline before repository resolution and binds that resolution, the initial raw index snapshot, one bounded `git cat-file --batch` session, bounded frontmatter parsing and semantic validation, structured per-path validity, and identical final raw index revalidation to the same deadline. Exact OID/type/size/content framing, entry/field/list/issue budgets, duplicate-ID group invalidation, and byte, record, and stderr bounds all fail closed.
The helper supports only macOS and Linux and rejects every other platform, including other POSIX systems, before selecting or executing Git; this keeps its bounded process-group and filesystem guarantees explicit instead of silently weakening them. When Python exposes POSIX `waitid`, status is observed with `WNOWAIT`. On macOS runtimes without `os.waitid`, including Xcode Python 3.9.6, the parent registers a one-shot kqueue `NOTE_EXIT` observer immediately after `Popen`; registration-time `ESRCH` counts only for the direct child that this parent has never polled or waited, proving it already became an unreaped zombie. Both paths keep that unreaped direct child as the PID/PGID identity fence through every bound process-group probe and signal, and the kqueue path obtains the exact return code only from the final post-cleanup `wait()`. After Linux confirms that leader has exited, a bounded `/proc` scan excludes the retained zombie leader while proving whether any live nonleader still belongs to the group; macOS retains signal-zero group probes. Successful and failed commands both complete process-group cleanup before the leader is reaped, so a zero-exit wrapper cannot leave a detached descendant behind. Explicit cleanup ownership states close the async-exception handoff between process-group cleanup and reap-only cleanup; the helper never signals a numeric PGID after the final reap and reports `cleanup-incomplete` if identity, ownership handoff, or cleanup cannot be verified. Error-path cleanup reuses the already claimed ownership object; if cleanup itself raises, only a proven reap-only state permits the final reap, and bounded cleanup exception evidence attaches to the original action exception instead of replacing it.
CLI parsing, including `--help`, completes before Git runtime initialization. Git runtime initialization and one command dispatch then share a single deferred-signal lifetime. Before either begins, the macOS/Linux helper requires working POSIX `pthread_sigmask`, `sigpending`, and synchronous `sigwait` support (using libc `sigwait` when Python does not expose it) and fails closed if any primitive is unavailable. It blocks candidate `SIGHUP`, `SIGTERM`, and `SIGQUIT` signals while installing handlers, leaves `SIG_IGN` and caller-blocked signals untouched, then records only the first managed request without doing cleanup in the handler. Bounded checkpoints route that request through process-group reaping and hook transaction-state reporting. At terminal exit the helper blocks every actually managed signal and unconditionally commits process-private Git runtime cleanup—even after a normal command—before restoring handlers; all Git subprocesses for that command have already finished, and a later in-process `main()` invocation creates a fresh runtime. A terminal cleanup with no retained runtime also clears a cached initialization failure so a repaired `PATH` can retry; incomplete cleanup keeps the retained runtime and locator-bearing error. If terminal mask acquisition fails, outer convergence still commits runtime cleanup, retries the mask only after that commit, and otherwise performs best-safe handler and known-mask restoration plus active-state reset before surfacing the original failure. While still masked it repeatedly uses `sigpending` plus `sigwait` to consume requests that arrived during cleanup or handler restoration, restores the original handlers, requeues only the recorded first signal, and atomically restores the prior mask. Thus `SIG_DFL` terminates, a custom handler runs once and may return, ignored signals remain ignored, and a signal arriving in the final check-to-unmask window sees an already terminal runtime state. When the protected action itself fails, that exact action exception remains primary even if terminal convergence also fails; bounded convergence details, existing action recovery notes, and any retained runtime cleanup locator remain attached as notes, including on Python runtimes without `BaseException.add_note`. Pending-signal reporting reserves its final bounded detail slot for a runtime cleanup issue, so a saturated action-note list cannot hide the retained locator. A cleanup failure is reported with its retained locator before original signal propagation, and the bounded CLI note remains visible when a command error also occurred.
Opt-in hook installation supports macOS and Linux only. It accepts system configuration only when `GIT_CONFIG_NOSYSTEM=1` disables it or `GIT_CONFIG_SYSTEM` names an explicit absolute path; an implicit build-dependent system path fails closed. Explicit system and global Git configuration are snapshotted through required `O_NOFOLLOW|O_NONBLOCK` descriptors, regular-file validation, and bounded double reads without following includes. If either scope sets `core.hooksPath` or contains an unresolved include, installation stops with an actionable repo-local override that names the durable selected source Git executable rather than a process-private snapshot. Effective worktree and local hook paths are queried through trusted Git with `--type=path --null`; Git expands `%(prefix)` and preserves significant leading or trailing whitespace before root constraints are applied. Hook writes bind the complete absolute path from the filesystem root, traverse and create allowed relative components with descriptor-relative no-follow operations, retain and revalidate every ancestor binding, and inspect existing targets with required `O_NOFOLLOW|O_NONBLOCK`. An owner-private lock serializes cooperating installers. Owner-private same-directory temporary files are committed with native no-replace or exchange rename semantics; an absent-target no-replace `EEXIST` or `ENOTEMPTY` is a definite uncommitted conflict, while any other rename error immediately revalidates exact target and staged snapshots. A proved committed rename continues directory durability and final verification, a proved uncommitted rename cleans its staging file, and an uncertain result preserves and reports the recovery locator. An absent, replaced, or content-changed target otherwise fails closed, and a mismatched exchanged entry is rolled back only while the installed object is still transaction-owned. A failed or uncertain rollback preserves the displaced object under a reported recovery locator. Before displaced-hook deletion, the helper verifies both the displaced and installed objects and enters an explicit installed-target-committed state. That committed state survives temporary-entry consumption, directory fsync, and final identity/content/access-policy verification, so a failure or asynchronous interruption reports an installed target with incomplete durability or verification instead of claiming installation failed or inventing a displaced recovery object. An asynchronous interruption before that state preserves the temporary entry and reports whether it verifies as the displaced-hook recovery object; an interruption during post-commit deletion reports either a retained cleanup locator or completed cleanup and never claims a missing recovery object. Every published recovery or cleanup locator is resolved from the held root-to-directory descriptor chain, accepts renamed components only after a bounded descriptor-relative identity/access-policy match, and is emitted only after revalidating the held directory and leaf object/type/ownership/mode/size/content binding. If the current path cannot be resolved safely, the report marks it `path_unverified` and records structured directory device/inode plus leaf and held-object evidence before closing the descriptors. Target protection covers path and target object identity, type, ownership, access mode, size, and content—not benign timestamp or directory child-entry churn. These checks detect ordinary concurrent installer races; they do not claim to exclude an actively malicious same-UID process that can ignore the protocol and mutate entries after a final verified kernel operation.
Repository discovery streams both active `sessions` and flat `archived_sessions` rollouts through one shared 60-second monotonic deadline and aggregate caps of 131,072 filesystem entries, 8,192 logical rollouts, 256 MiB each for logical rollout input and its second-pass verification reads, 4 MiB per line, 1,000,000 records, 4,096 normalized distinct CWDs, JSON depth 64, 4,096 digits per JSON integer, 16 KiB of strict UTF-8 per CWD, 256 CWD components, and 32 retained scan errors. The two sources share every counter and never reset either byte ceiling. Enumeration binds each rollout's regular-file identity and access policy; parsing reopens that exact object with required `O_NOFOLLOW|O_NONBLOCK`, rebinds the path, and then repeats a deadline-checked digest read bounded by the exact first-pass size before final descriptor/path revalidation. A FIFO, symlink, unreadable path, object replacement, content change, or other unstable inspection marks coverage partial with a distinct `inspection_reason` instead of blocking or being treated as a missing rollout. Physical active/archive files with the same rollout basename are both consumed and their CWD evidence is unioned, while each repository association contributes only once to the logical `rollout_count`; an unreadable, malformed, invalid-UTF-8, or otherwise unprovable copy makes coverage partial instead of being hidden by basename deduplication. CWD byte and component caps are enforced before `Path` construction or repository fallback. `coverage_status: complete` proves the candidate scan stayed within those bounds; a deadline, limit, non-empty record parse failure, invalid CWD encoding, or source I/O failure preserves rows already found but marks every row `partial` with structured `discovery_coverage` evidence, and emits an inconclusive sentinel row when no repository was found. Consumers must not interpret a partial or sentinel result as a complete candidate set.

Within that bounded candidate set, `adoption_status` is the authoritative `adopted`, `unadopted`, or `inconclusive` tag; inconclusive rows include a structured `adoption_error` and null adoption fields, and consumers must not use them as unadopted evidence. Each candidate gets one absolute deadline, capped by the aggregate scan deadline, before bounded repository resolution. Resolution, adoption, journal enumeration, generated-index classification, exclude lookup, hook resolution and inspection, and index presence checks all consume that same deadline instead of resetting independent timeouts. When another CWD resolves to the same root with at least one additional second of remaining budget, a still-inconclusive adoption check receives one retry; each root is enriched at most twice, so persistent failures remain bounded. Auxiliary per-repository failures produce a field-keyed structured `discovery_error` and null only the affected auxiliary fields without erasing authoritative index adoption or aborting healthy repository rows. Generated-index marker, exclude, and hook reads require no-follow/nonblocking descriptors bound to stable regular files and enforce hard retained-byte ceilings; the marker classifier reads only a 4 KiB/2 KiB-per-line three-line marker prefix. A truly missing entry is an authoritative negative, while a deadline, EACCES, EIO, FIFO, symlink, directory, unstable file, or oversized input produces structured partial/limit evidence and leaves only the affected field unknown. Inaccessible journal, index, exclude, or hook paths therefore remain unknown rather than becoming false or zero. In particular, unresolved effective hook configuration makes `hooks_installed` null and the discovery row inconclusive; `false` remains reserved for an authoritative negative check.

## Cleanup failure precedence

Snapshot cleanup during creation, the version probe, or final validation follows the same failure precedence as launch cleanup: an active failure remains the exact primary exception with bounded retained-locator evidence, while a cleanup failure with no active exception becomes the reported initialization failure.

Terminal runtime cleanup converts an ordinary `Exception` into the locator-bearing cleanup issue. A non-`Exception` `BaseException` such as `KeyboardInterrupt` or `SystemExit` instead receives bounded retained-locator evidence. When that interruption is the sole terminal failure and no managed signal is being propagated, it is re-raised without replacement, preserving the same object, type, arguments, and traceback. Against the cleanup failure, an active action exception remains primary and receives the cleanup evidence; existing precedence for an earlier terminal-convergence failure or managed-signal propagation is unchanged.

If cleanup of an uncommitted hook staging entry fails while another installation error is active, that exact installation error remains primary and receives bounded descriptor-bound locator evidence after path verification; an unresolved path is reported as structured `path_unverified` evidence instead. Without an active error, the cleanup failure is reported on its own.
